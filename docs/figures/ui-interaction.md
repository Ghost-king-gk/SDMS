### 1.1 技术选型（2026-10-14 答复确认）

| 项 | 结论 | 说明 |
| --- | --- | --- |
| GUI 框架 | **PySide6（Qt for Python）** | ljj 2026-10-14 答复：用 PySide，版本取当时最新稳定版，理由是原生控件的呈现效果明显好于 Tkinter |
| 存储 | **SQLite** | 同上答复：比 MySQL 轻量，不需要起服务进程；用标准库 `sqlite3`，不引入 ORM |
| 目标平台 | **Windows**（桌面 GUI） | zch 2026-10-16 答复：Linux 侧不做 GUI 适配，先把 Windows 端做完；作为交换，**界面与后端之间要留好替换入口，不作强耦合**，详见第 11 节 |

**版本策略。** `pyproject.toml` 声明 `PySide6>=6.11.2,<7.0`，实际版本由 `uv.lock` 锁定，取该区间内最新稳定版。截至 2026-10-14，PyPI 上最新稳定版为 **6.12.0**（2026-10-08 发布，要求 Python `>=3.10,<3.16`，本项目 3.12.x 在范围内）。版本锁一次，中途不随手升级；确实要升就走 PR 并说明原因。

**依赖合规。** PySide6 是第三方包，按 `AGENTS.md` 要求记录来源、版本与许可证：来源 PyPI（`pypi.org/project/PySide6`），许可证 `LGPL-3.0-only OR GPL-2.0-only OR GPL-3.0-only`（本项目按 LGPL-3.0-only 条款使用）。**这也是选 PySide6 而不是 PyQt6 的原因**：两者 API 基本一致，但 PyQt6 在 GPL 之外需要商业授权，PySide6 是 Qt 官方绑定，条款更宽松。

**一个必须解决的合规点。** `Requests/日程管理系统.md` 的「文档」节明文要求：**「如果有用到第三方的包，放在 src 目录下的 lib 子目录下」**。这条比 `AGENTS.md` 的软性表述更硬。这不是理论担心——本机实测安装后 `PySide6` 包目录为 **646.7 MB**（含 Qt 运行库与可选组件，见 8.2 节实测记录），且其中的二进制扩展绑定平台：把 Windows 上装好的 Qt 运行库整包拷进 `src/lib/`，Linux 侧无法复用，提交包还会大到交不上去。处理办法见第 9 节 T-01，属于**必须有人拍板**的合规项，不能默认跳过。

**选型代价与回退。** 代价是 `dependencies` 不再为空，环境搭建多一步 `uv sync`，且必须在 Windows 上验证 `import PySide6` 与创建窗口成功（V-17）。若后期因环境原因回退 Tkinter，本文的布局、状态机、交互规则与验收用例全部成立，只需替换控件类名——这也是把它们写在文档里而不是写在代码里的原因。

**平台范围。** 桌面 GUI 的目标平台是 **Windows**，Linux 侧不做 GUI 适配，也不为它排期、不要求复跑验收清单。代价是字体度量与控件默认尺寸的差异只在 Windows 一侧被验证过；收益是 P10 的工期全部投在一端，先把东西做出来。这条不影响第 11 节的可替换性——正因为前端是可替换的，将来补一个 Linux 端或其它形态的前端才不需要重写后端。

**日期控件不再自绘。** 原先「标准库 `calendar` + `ttk` 自绘月历」的方案建立在 `dependencies = []` 之上，该前提已经消失。Qt 自带 `QCalendarWidget`，跨月、闰年、周起始都由控件保证，`tkcalendar` 更无必要。见 5.1 节。

## 3. 总体布局

主窗口采用**顶部工具栏、左日历、右列表、底部状态栏**的四段式，见 `ui-wireframe-main.svg`。

| 区域 | Qt 控件 | 职责 |
| --- | --- | --- |
| ① 日历选择区 | `QCalendarWidget` | 显示月历、跨月前后缀日期（控件内建）、切换月份、回到今天、标记有日程的日期（**标记项尚未实现**，见 12.6 节） |
| ② 当前日期条 | `QLabel` | 显示当前筛选日期与当天日程条数 |
| ③ 日程列表 | `QTableWidget` | 三列（时间 / 标题 / 备注），每行 `Qt.UserRole` 绑定 `schedule_id`，按时间、id 确定性排序 |
| ④ CRUD 工具栏 | `QToolBar` + `QPushButton` × 6 | 新增、查看、修改、删除、刷新、退出，**统一置于画布上侧** |
| ⑤ 状态栏 | `QStatusBar`（内含 `QLabel`） | 显示最近一次操作结果与当前选中项 |

控件列的 Qt 类名是「推荐实现」，不是契约本身；契约是每行的职责与第 5 节的行为。换用 `QTableView + QAbstractTableModel` 这类 Model/View 写法同样允许，只要③的行为不变。

四条布局约束：

- **操作按钮置于上侧**。新增、查看、修改、删除、刷新、退出统一放进顶部工具栏，不放在窗口底部。工具栏是用户的第一落点，位置固定才能形成肌肉记忆。
- **行标识与显示分离**。列表显示的是格式化文本，但每一行必须通过 `Qt.UserRole` 关联 `schedule_id`（UUID 文本）。禁止用行号或标题反查记录——标题可重复，行号会随排序变化。
- **首次启动显示当天**。空库也要有清晰的空状态，不能是一片空白让人以为程序坏了。
- **日历必须覆盖跨月与闰年**。`QCalendarWidget` 内建这两项能力（`setMinimumDate` 等不当设置才是唯一风险），但仍要目验一次（V-07）；周起始按国内习惯设为**周一**（`setFirstDayOfWeek(Qt.Monday)`），默认周日是 Qt 的原生行为，不改会让全组截图不一致。

## 5. 交互规则

以下规则来自契约草案第 4 节，UI 侧必须遵守。每条都指向一项可以被单测或人工验证的行为。

### 5.1 日期与时间的输入

**界面不预先拦截用户的日期写法。** 它只做两件事：提供选择入口，把原始文本交给后端。

- **优先选，也允许写**。日期字段用 `QLineEdit`，旁边固定一个「选择」按钮，点开日历浮层（`ui/date_picker.py`，内部就是一个 `QCalendarWidget`），点选某天后回填标准格式文本；用户也可以直接在输入框里手写。两种入口地位对等，不因为提供了日历就禁用键盘输入。
- **不用 `QDateEdit` 当日日期框**。`QDateEdit` 会先按控件的显示格式做一次强校验，用户手写的 `2026/10/15`、`10月15日` 会被控件在提交前就拦掉，等于把「是否合法」的判断权拿回了界面层——这与下面的分工冲突。`QDateEdit` 只适合内部工具与其它不要求宽容输入的 Qt 场景。
- **主窗口日历不再自绘**。左侧①直接用 `QCalendarWidget`，`ui/date_picker.py` 只把它包成一个浮层小部件，两者共享同一个「有日程的日期如何标记」的绘制函数，不各自实现一遍月历算法。
- **宽容解析属于后端职责**。`2026/10/15`、`2026.10.15`、`10月15日` 这类写法的统一识别与转换是一条业务规则，放在后端的转换环节实现，界面不判断「格式对不对」，也不弹「日期格式不正确」。
- **界面的职责是呈现结论**。解析或校验失败时，显示的是**后端返回的原因**，而不是界面自己编的格式要求。字段级红框是后端结论的呈现方式，不是前端拦截的产物。
- 标准格式：日期 `YYYY-MM-DD`，时间 `HH:MM`，分钟精度，本地朴素时间，不处理时区。这是**回填与显示**用的格式，不是对用户输入的准入条件。
- 标题去首尾空白后非空；备注允许为空。这两条同样是后端判定的结论。

### 5.2 写入成功与失败

- **写入成功后**才刷新列表并提示成功。
- 写入失败时**保留表单与已填内容**，提示后端给出的失败原因。任何情况下不得假装成功。
- **异常处理的权威在后端**：是否合法、记录是否存在、存储是否可用，全部由服务层判定。界面不做平行判断，也不重复实现一遍校验规则，只把后端返回的结构化错误翻译成用户能读懂的句子。
- 只有可解释的预期错误（`ValidationError` / `ScheduleNotFound` / `StorageError`）被转换成用户提示；意外异常记录诊断信息并给通用提示，不静默吞掉，也不把裸堆栈甩给用户。
- 注意边界：服务层**不能弹窗**。后端负责「判定并抛出」，界面负责「捕获并呈现」，两者缺一不可。把异常「交给后端」不等于界面不显示错误。

### 5.3 删除的两条路径

这是本轮最容易写错的地方，两张流程图就是为它画的。

**未选中时点击删除**（`ui-delete-flow-unselected.svg`）：controller 读到 `selected is None`，就地提示「请先选择一条日程」并返回。**整条链路零次服务调用**——未选中是界面状态问题，不是业务错误，不应当产生一条 `ScheduleNotFound`。

**选中后点击删除**（`ui-delete-flow-confirm-cancel.svg`）：

- 确认框弹出时**服务尚未被调用**。
- 点「取消」→ 对话框关闭，列表与数据不变，`service.delete` 一次都不调用。
- 点「确定」→ 才调用 `service.delete(schedule_id)`；记录是否存在由服务层校验，UI 不替它判断。
- 成功 → 刷新列表；失败 → 提示并保留原状。

删除确认属于**交互策略**，不能替代服务层的有效性校验。即便 UI 已经确认过，服务内部仍要处理记录不存在的情况。

### 5.4 选中与切换

- 无选中项时点击「修改」或「删除」，提示先选择日程，**不把 `None` 传给服务**。
- 切换筛选日期后清空选中项并刷新列表。
- 修改日期后，被修改的记录从当前列表移出是**正常行为**，不是 bug；此时刷新当前筛选日期即可。

最初设计的映射里没有 `main_window.py`，实现时把它拆了出来：`app.py` 只负责进程级的事（创建 `QApplication`、注入服务），窗口本身与 `MainViewPort` 的实现放在 `main_window.py`。这样"入口"与"窗口"可以各自替换——例如将来做 CLI 前端时，`app.py` 换成 `cli_app.py`，而 `main_window.py` 原样留着。

分层约束（违反即视为设计错误）：`ui` 不 import `sqlite3`，不拼 SQL；**领域层不 import `PySide6`**（也不 import `tkinter`——换框架不改这条）；服务层不弹窗；**模块导入时不得创建 `QApplication`、不得弹窗、不得连接数据库**（这是最容易踩的一条：pytest 收集阶段一旦触发窗口创建，在没有显示服务的环境里会直接挂掉，自动化测试连收集都过不去）。

`QApplication` 只允许在 `ui/app.py` 的 `main()` 里出现一次。写成模块级 `app = QApplication([])` 会污染导入，也会让未来的 GUI 测试无法自行管理事件循环。

### 10.1.1 守卫为什么改成按角色分档

P09 阶段守卫是一条一刀切的规则（`ui` 包不许 import 任何 GUI 运行库）。P10 要写窗口，这条直接把它拦死了，于是改为两档：

| 类别 | 模块 | 禁止引入 |
| --- | --- | --- |
| 与呈现无关 | `__init__`、`view_models`、`ports`、`presenters`、`controller` | `PySide6`、`tkinter`、`sqlite3` |
| 窗口适配器 | `app`、`main_window`、`calendar_view`、`date_picker`、`schedule_form` | `tkinter`、`sqlite3`（**允许 `PySide6`**） |

两档之间还有一条元断言：**`ui` 包里每个模块都必须出现在上面某一档**。新增模块忘了归类会直接测试失败，而不是悄悄获得"什么都能 import"的自由。

注意窗口适配器仍然不许碰 `sqlite3`——分工红线不因为"这是前端"而放松；也仍然不许碰 `tkinter`（同为 GUI 运行库，同为兼职就能避免的东西）。

**为什么 `controller.py` 与 `presenters.py` 不许碰 Qt。** 这两块是全部交互规则所在地，一旦 import 了 `PySide6`，pytest 收集阶段就会在没有显示服务的环境里挂掉，界面逻辑也就没法脱离界面被测试。第 7 节那条约束现在有测试兜底了：谁手滑 import 了 Qt，`tests/unit/test_ui_layering.py` 会直接失败，并且报错信息会写清原因。

这条约束同时是第 11 节"前端可替换"的技术前提：**交互规则不依附于任何一种呈现技术**，所以换掉呈现方式时它们原封不动。

### 10.2 三个端口（界面层唯一的对外依赖方式）

| 端口 | 谁来实现 | 界面拿它干什么 |
| --- | --- | --- |
| `ScheduleLike` | 领域层的 `Schedule` 只要具备 `id / title / date / time / notes` 五个属性即可 | `presenters` 把它转成列表行，不需要 import 领域类 |
| `ScheduleServicePort` | 由 zch 的 `application/service.py` 落地；在此之前用 `ui_fakes.FakeScheduleService` | 四个用例：`list / create / update / delete` |
| `MainViewPort` | 由 P10 的窗口代码适配 | 九个单向输出 + 两个提问（`ask_delete_confirm`、`open_schedule_form`） |

全部用 `typing.Protocol` 的**结构性类型**：真实现换进来时 controller 不用改一行，`mypy` 负责证明它对得上（`mypy src tests` 当前全绿，说明替身与协议是严格匹配的，不是"跑得通就算"）。

### 10.3 与契约草案的唯一偏差：create / update 收原始字符串

计划第 4 节写的是「create/update 的 `day` 与 `at` 已经是日期/时间对象；GUI 字符串解析在 controller」。**这句话已经被 zch 在 PR #5 的第 1 条意见改写**：日期由用户手写或日历点选，统一交给后端的转换算法处理，界面不做准入检查。因此端口签名为：

```text
list_schedules(day: date) -> Sequence[ScheduleLike]
create_schedule(title: str, date_text: str, time_text: str, notes: str) -> ScheduleLike
update_schedule(schedule_id: str, title: str, date_text: str, time_text: str, notes: str) -> ScheduleLike
delete_schedule(schedule_id: str) -> None
```

`list_schedules` 仍然收 `date`：这个值来自日历控件的点选结果，本身就不是自由文本，不涉及"宽容解析"。

**这条偏差必须写进 `docs/design/contracts.md` 才算定稿**，否则 zch 按原草案写出 `day: dt.date` 的签名，两边就对不上了。

另一个关联决定：`presenters.error_category` 目前按**异常类名**判定而不是 `isinstance`，因为 `domain/errors.py` 与 `application/errors.py` 还没落地，界面不能在导入期依赖它们。`tests/unit/ui_fakes.py` 里的三个假异常类特意与契约同名（`ValidationError` / `ScheduleNotFound` / `StorageError`），就是为了覆盖到这条路径。真异常类可用后，把该函数体换成 `isinstance` 判定即可，调用方无需改动。

**为什么需要它。** 后端三层由 zch 与 xhy 负责，`contracts.md` 也还没定稿。若按"后端就位再验界面"的顺序排队，
界面就会一直停在纸面上：既拿不到截图，也无法做第 6 节那份人工验收，最终把风险全压到最后几天。有了替身，
界面现在是**能双击打开、能新增、能删除、能截图**的程序，验收清单可以先跑一遍。

**它替不了什么。** 一律明确标注：替身**验不了持久化**（V-14），也验不了 xhy 的 SQLite 约束（唯一键、并发、事务）。
它验的是"界面与交互规则对不对"，不替代"数据存不存在"。

**它对 xhy 反而有用。** 33 项替身测试（`tests/unit/test_dev_stub_service.py`）把边缘行为写死了——
空标题怎么处理、删不存在的记录怎么报、同一天日程如何排序。这些正好是 SQLite 真实现要照着对齐的规格，
他不必从零猜。

**下线方式。** 真服务落地后，只改入口那一行注入即可：`ScheduleController` 依赖的是 `ScheduleServicePort` 协议
而不是具体类，替身与真服务对协议的实现由 `mypy` 证明等价。

### 10.6 P10 已落地，验收覆盖面随之扩大

`scripts/shoot_ui.py` 会开真正的窗口、截真正的图，并把不需要人眼判断的部分断言掉（当前 **8 项全过**）：
V-01 启动显示当天、V-01 六按钮齐备、V-05 选中同步、V-06 空状态、V-07 闰年可构造、V-16 不可识别日期原样离开表单。
逐条实测值与仍然只能人工验的部分见 **12.4 节**，这里不重复。

两点必须说清：

- **必须在桌面会话里跑**：离屏模式下 `QFontDatabase` 返回 0 个字体，中文会渲染成方块，那种截图没有验收价值。
- **替身验不了持久化**：V-14 在这套环境里**必然验不过**，它要等 xhy 的 SQLite。程序能开能删，不等于数据存得住。

截图、环境版本（Python 3.12.14 / PySide6 6.12.0 / Qt 6.12.0）与复现命令归档在 **`docs/screenshots/README.md`**，V-17 要求的版本号就记在那里。

## 11. 目标平台与前端可替换性

本节由 2026-10-16 的第二轮审查（8.3 节）催生，回答的问题是：**只做 Windows 端，为什么还要留接缝，接缝具体在哪。**

### 11.1 只做 Windows，不等于可以把前后端焊死

桌面 GUI 的目标平台是 Windows，Linux 侧不适配。但「只做一端」是排期决定，不是架构决定——如果把业务逻辑写进窗口代码里，将来无论加 Linux 端、加 CLI 还是加 WebUI，都得先做一次外科手术把它挖出来。反过来，接缝留住了，补前端是**新增**一个适配层，不是**重写**。

分工边界（与第 1 节一致，这里从可替换性的角度重申）：

| 侧 | 负责 | 不许碰 |
| --- | --- | --- |
| 后端（domain / application / infrastructure） | 数据是否合法、记录是否存在、存储是否可用、日期文本如何解析 | 不许 import `ui`，不许弹窗，不许知道用户在用窗口还是终端 |
| 前端（ui） | 呈现、采集用户输入、把后端结论翻译成用户能读懂的句子 | 不做平行校验，不 import `sqlite3`，不拼 SQL |

### 11.2 接缝就是两个 Protocol

`ui/ports.py` 里那两个协议就是全部接缝，见 10.2 节。它们之所以能当接缝用，是因为 `controller` 只按协议说话，不按实现类说话：

| 端口 | 当前实现（Windows 桌面） | 未来可换成的实现 |
| --- | --- | --- |
| `MainViewPort` | P10 的 `ui/app.py` 适配的 `QMainWindow` | `CliMainView`（输出打 stdout，提问用 `input()`）、WebUI 的 HTTP handler、乃至测试里的 `FakeMainView` |
| `ScheduleServicePort` | zch 的 `application/service.py` | 任何满足同样四个方法的服务；换存储不影响这一层 |

`MainViewPort` 的十一个方法（九个单向输出 + `ask_delete_confirm` / `open_schedule_form` 两个提问）就是**前端必须兑现的全部契约**。新前端只要兑现这十一个方法，就能接上现成的 `ScheduleController`。

### 11.3 将来换一个前端，动什么不动什么

以 CLI 前端为例（**现在不实现**，只作为接缝的验证口径）：

| 动作 | 内容 |
| --- | --- |
| 要新增 | `schedule_management/cli/`（或 `ui/cli_main.py`）：一个实现 `MainViewPort` 的 `CliMainView`，加一个 `main()`，把 `ScheduleServicePort` 的真实现与 `CliMainView` 一起塞进 `ScheduleController` |
| **不用改** | `view_models.py`、`ports.py`、`presenters.py`、`controller.py` 四个文件；后端三层的任何文件；`tests/unit/` 里针对这四块的测试（当前 108 项，本就跑在无窗口环境里） |
| 不用删 | 桌面端的 `ui/app.py` 等——两种前端可以共存，靠入口区分 |

WebUI 同理：新增一个 `web/` 包，在请求处理里适配 `MainViewPort` 即可。**交互规则只有一份**，不存在「桌面版规则」和「网页版规则」两套。

### 11.4 三条保证接缝不被焊死的硬约束

1. **与呈现无关的四块不许碰 GUI 运行库**。`view_models` / `ports` / `presenters` / `controller` 不得 import `PySide6`、`tkinter`、`sqlite3`，由 `tests/unit/test_ui_layering.py` 用 AST 扫描强制。
2. **第 5 节的交互规则不引用控件类名**。它只讲「调用什么、显示什么结论」；第 3 节的控件列是推荐实现而非契约（原文已注明），因此换控件不影响规则成立。
3. **依赖方向单向**。ui → 端口 → 后端，后端不反向 import ui。第 10.1 节那条「controller 不许碰 Qt」是这条的落地点。

### 11.5 现在不做的事（避免过度设计）

- **现在不写 CLI 前端代码，也不引入任何 Web 框架**。预留的是接缝，不是提前把三种前端都实现一遍——那样只会多出两个没人用的半成品。
- P10 的唯一额外要求：`ui/app.py` 只做 `MainViewPort` 的适配，**交互规则一律留在 `controller.py`**，不因为「窗口里写起来更顺手」就搬进去。
- 可验收的判据（随时可查）：**若要把交互规则搬到另一个前端，需要改动 `controller.py` 或 `presenters.py`，即判定为耦合，须回头修接缝**；只需新增一个 `MainViewPort` 实现即视为接缝有效。这条判据不看主观感受，看改哪些文件。

## 12. P10 落地说明（2026-10-16）

图形界面从文档变成了能打开的程序。这一节记录它怎么跑、替身服务是什么、
哪些验收项真的验过了、以及哪些**没验过**——最后一项比前几项更需要写清楚。

### 12.1 现在能真的跑起来

```bash
uv sync                                   # 首次安装 PySide6（本机实测约 1 分钟，含缓存）
uv run python -m schedule_management.ui.app   # 直接启动
uv run python scripts/shoot_ui.py             # 跑一遍场景并产出截图
```

`pyproject.toml` 的 `dependencies` 从空列表改为 `PySide6>=6.11.2,<7.0`，与 1.1 节的版本策略一致。**声明依赖不等于把二进制整包入库**：`src/lib/` 那个课程合规问题（T-01）仍未拍板，两者是两件事。

程序启动后落到当天，左侧月历（周一起始）、右侧当日列表、顶部六个按钮、底部状态栏，与第 3 节的四段式一致。

### 12.2 开发替身服务：`dev_stub_service.py`

真服务还没落地，界面要跑起来就得有个东西顶着。这个文件就是**为了不让人闲着**而写的替身，边界说清楚：

| 它做了什么 | 边界 |
| --- | --- |
| 日期时间的宽容解析（`2026/10/15`、`2026.10.15`、`2026年10月15日`） | 只认分隔符差异，不认 `明天`、`下周三`；最终范围以 `contracts.md` 的 T-02 为准 |
| 字段校验（标题去空白非空、长度上限） | 上限值是 T-04 的暂定值，不是课程规定 |
| 增删改查 | **全在内存里，退出即丢** |

三件本属后端的事被它临时做了，所以它**不是** `application/` 或 `infrastructure/` 的替代品，更不是替谁完成作业。真实现到位后，`ui/app.py` 的 `build_service()` 换掉即可，界面与 controller 一行不改——这正是第 11 节那个接缝的第一次真实检验。

### 12.3 分层守卫按角色分层

P10 引入了真正 import `PySide6` 的窗口模块，原先"`ui/*.py` 一律不许碰 GUI"的守卫会连自己的实现一起拦死，因此改成按角色判定（`tests/unit/test_ui_layering.py`）：

| 名单 | 模块 | 禁止 import |
| --- | --- | --- |
| 与呈现无关 | `__init__`、`view_models`、`ports`、`presenters`、`controller` | `PySide6`、`tkinter`、`sqlite3` |
| 窗口适配器 | `app`、`main_window`、`calendar_view`、`date_picker`、`schedule_form` | `tkinter`、`sqlite3`（**允许 `PySide6`**） |

两条兜底：`sqlite3` 对**全包**禁止（界面不碰存储这条红线不因为"它是窗口"就放宽）；新增模块若没有被登记进任何一张名单，守卫会失败——宁可逼人补一行登记，也不让模块悄悄溜过去。

### 12.4 本轮实测结果（含**未验项**）

`uv run python scripts/shoot_ui.py` 在真窗口下跑一遍：**8 项全通过**。

### 12.6 本轮明确没做的事

- **日历上给有日程的日期加标记**。`calendar_view.mark_days()` 已经写好，但标记需要"这个月哪些日期有日程"的数据，那要求后端提供按月查询（建议 `list_days_with_schedules(month)`）。窗口绕开 controller 自己去遍历查询会破坏第 11 节的接缝，所以宁可先留白。**这是端口待扩展项，需与 zch 确认后写进契约。**
- 键盘快捷键、右键菜单、拖拽调整等增强交互——不属于课程要求的六个状态。
- 真实持久化：见 12.4 节最后一行。
- 日期时间解析的"正式版本"：替身里那份是临时最小实现，T-02 拍板后由后端接管。
